# 2026-09-29 修「连不上路由器」+ 猫猫核心起不来

## 现场
- 用户换到 ZTE U30Pro（Android 内核 5G CPE，192.168.0.1），Mac 拿到 192.168.0.113。
- 设备列表里还留着旧路由器 Rax3000M（192.168.10.1）—— 该地址在新网段**会超时**（SYN 被丢），
  是"请求超时"文案的一个来源。
- App 报「请求超时，请关掉系统代理」；实测**系统代理全关**，网络与代码都正常。

## 排查结论（重要）
1. **网络本身没问题**：curl / Python / 同构 Swift（完全一样的 URLSession 配置）打
   `192.168.0.1:2333` 都是 50ms 内 200。
2. **本地网络权限不是原因**：`/Library/Preferences/com.apple.networkextension.plist`
   （可读！）里 `dev.don.ClashRemote` 是**已授权**（MulticastPreferenceSet=true / DenyMulticast=false），
   而且有 **两条重复记录**（dist 路径 + /Applications 路径）。
   → 排查 macOS 本地网络权限可以**直接读这个 plist**，不用去点系统设置。
3. **真正的根因在猫猫侧**：`/data/clash/Proxy/config.yaml` 被 ClashRemote 覆盖成了
   **365 字节的残片**（只剩 `proxy-providers:`），`proxies`/`proxy-groups`/`rules` 全丢。
   `clashctl` 因此判定 `空文件, 插件已停止运行` → 核心不启动 → Clash API :7788 不监听 → App 连不上。
4. **写入链路缺陷**：`UFIClient.rootShell()` 在响应里没有 `result`/`content` 时 **静默 `return ""`**；
   `readFile` 又只是 `cat`，不校验大小；`insertProvider` 于是把"读空"当成"文件本来就空"，
   从零拼出一份只有 proxy-providers 的配置写回去 → **数据丢失**。
   `writeFile` 也不核对落盘大小，大文件经 root shell 传输被截断同样无声。
5. **误导性文案**：超时一律甩锅"系统代理"，实际成因是路由器没应答/端口不通/服务端忙。
6. **UFI-TOOLS 的 Ktor 服务端在长命令执行期间会整体阻塞**（实测 `GET /` 直接超时），
   所以并发请求会超时 → 这是 -1001 而不是"连接被拒 -1004"的机制。
   长命令：`Clash.Service restart`、`downloadSubscription`(120s)、`runDeviceFailoverOnce`(40s)。

## 第三轮：「同步卡住」的根因（02:42）

### ⚠️⚠️ `Clash.Service restart` 是无效参数（旧代码 + 我第一版都踩了）
- `clashctl` **只认 `start|stop`**，传 `restart` 直接被拒（打印"只能使用start|stop两个参数"），
  **且失败是静默的**（退出码非 0，没人看输出）。
- 症状：清单写进 config.yaml 了（156 字节两行清单），但**核心没重启 → clashctl 不会去展开清单**，
  于是"等 proxy-groups 出现"的循环白等 40s，用户看到的就是"卡住"。
  （包装脚本的 case 只处理 start/restart/stop 来拉 node-failover 守护，**REAL 先被调用并失败**。）
- 修：`MaoMaoService.restart()` 用 `stop; sleep 1; start`，超时 40s → **180s**（start 会重下订阅+规则集，慢是正常的）。
  `commitConfig` 原本也用了 `"\(servicePath) restart"` —— 一起改成走 `restart()`。
- **验证落地的正确姿势**：看 `config.yaml` 是不是从"两行清单"变成了带 `proxy-groups:` 的完整配置；
  看 `proxies/providerN.yaml` 的 mtime 有没有更新。

### 轮询抢通道（性能）
- App 每 3 秒轮询 `refresh` + `refreshDeviceFailover`（后者是 root shell）。
  长操作期间它和长命令抢同一条通道，而 **UFI 服务端执行长命令时整体阻塞** → 互相等，表现为卡死。
- 修：`AppState.run()` 在长操作期间 `pollTask?.cancel()` + 停掉 failoverTask，结束（含失败/取消）后 `startPolling()`。
- 另：`applySubscriptions` 的等待循环从"每轮 readFile 整个配置（展开后 180KB+）"改成
  `grep -c '^proxy-groups:' <file>`，间隔 2s→3s，最多 30 轮。

## 第五轮：订阅 tab 显示三个 + URL 是 health-check 的 bug（03:05）

### 症状
订阅 tab 显示 `provider1/2/3`，**三条 URL 全是 `https://www.gstatic.com/generate_204`**。

### 根因
`MaoMaoService.urlLine(in:)` 取的是"provider 块里第一个 http(s) 的 `url:`"，
而 **clashctl 生成的 proxy-providers 里的键是按字母序排的**：
```
    provider1:
        health-check:
            url: https://www.gstatic.com/generate_204   ← 排在最前面，被误取
        ...
        url: https://yuyun.mhlnf.cn/...
```
→ App 把健康检查地址当成了订阅地址，点「更新」会去下载那个 204 页面。
provider3 是插件模板的空占位槽（`url: 你的订阅链接3`），本来就不该显示。

### 修法
`urlLine` 改为**按缩进只认 provider 自己那层（最浅一层）的 `url:`**，
并且要求值是 http(s) 开头 → 占位槽自动被过滤掉。
- 验证：`provider1 → 渔云`、`provider2 → 乌拉`、`provider3 → nil（不显示）` ✅

### 未做（有意）
没把显示名改成「渔云/乌拉」：`Subscription.name` 同时被「更新」按钮用来
`updateConfig(filename:)` 匹配 provider 名，改名会让「更新」失效。
所以 tab 里仍是 `provider1` / `provider2`（顺序 = 清单顺序）。

## 第六轮：「路由器上没有 config.yaml」误报（03:10）

### 症状
用户给订阅改名 + 点「同步订阅和规则」都报 `路由器上没有 config.yaml`。
实测文件**存在**（9464 字节），App 用的那条命令现在跑也正常 → **瞬时窗口误报**。

### 根因（我的 bug）
`UFIClient.readFile` 只读一次，遇到 `[ -f ]` 为假就抛"路由器上没有 …"。
而 **clashctl 重启时会重写配置（写两遍：生成 → 校验/规范化）**，
中间存在文件被短暂移走/替换的窗口。撞上就误报。

**后果比报错本身严重**：`syncAllToRouter` 里 `applySubscriptions` 之后的
`flattenPolicyGroups` 因此被跳过 → **方案 B 的收敛和过滤被冲回插件模板的 8 个组**
（核实：配置回到 选择节点/AIGPT/Bahamut/Netflix&Disney/Steam login/国内网站/拦截广告/漏网之鱼，
`exclude-filter` 计数 0，香港和垃圾节点全回来了）。

### 修法
1. `readFile` 拆成 `readFile`(带重试 6 次 × 2s) + `readFileOnce`。
2. `applySubscriptions` 的等待循环改成**组合探测**（一次 root shell 拿 大小+组数+md5）：
   `if [ -f F ]; then printf '%s %s %s' "$(wc -c <F)" "$(grep -c '^proxy-groups:' F)" "$(printf '%s' "$(cat F)" | md5sum | cut -d' ' -f1)"; else echo MISSING; fi`
   要求 大小>500 且 组数≥1 且 **连续两次探测到同一个 md5** 才继续 —— 等 clashctl 写稳。
   （这条组合命令已在路由器上实测可用。）

### 还原
`config.yaml.crbak` 正好是同步前的收敛后配置（8791 字节、含 exclude-filter），
拷回去重启即恢复：5 个组、香港 0、垃圾 0、默认节点 🇯🇵 日本01。

### 结论：猫猫的订阅**改不了名**
`provider1/provider2/provider3` 是 clashctl **按清单位置**生成的 provider 名。
在 App 里改名写进生成的配置，会在下一次**插件重新展开清单 / 重启**时被冲回原名；
而且 `Subscription.name` 还被「更新」按钮用来匹配 provider。→ 不要改名，按顺序/看 URL 区分。

### 备份目录（都在 /data/clash/Proxy/.backup-20260929/）
`config.yaml.pre-B-*`(收敛前) / `config.yaml.pythonB-*`(手工 B 版) / `config.yaml.keep-*` /
`config.yaml.template-*`(被冲回模板的版本) / `config.yaml.working-*` / `config.yaml.manifest-*`

## 第七轮（03:16）：用户问"加了过滤词但网页面板还能看到"

### 查证结论
1. **路由器根本没被推送**：`config.yaml.crbak` 的 mtime 还是 03:04（`applySubscriptions` 开头
   会 `cp configPath configPath.crbak`）→ **用户只是改了本地配置，没点「同步订阅和规则」**。
   router 上的 `exclude-filter` 仍是旧的那串（不含「解锁」「超时」）。
   App 自己的说明也写着："筛选会立即影响节点列表和本机自动切换；**重新安装设备守护后在路由器上生效**"。
2. **`cr-failover.html` 是 ClashRemote 自己注入的页面**，放在
   `/data/clash/Proxy/WebUI/zashboard/` 下、由 mihomo 的 external-ui 托管
   → URL `http://IP:7788/ui/cr-failover.html`。旁边还有 `cr-failover.json` / `cr-failover-history.json`。
   它读的是 **`/proxies` 全量节点**。
3. **`exclude-filter` 只作用于"组"**：被排除的节点只是不在策略组里，`/proxies` 全量里仍然存在
   → 任何"列出所有节点"的界面都会看到。**要看是否生效，只能看 `<组名>.all`。**

### 待办 / 建议
- 让用户点一次「同步订阅和规则」把新关键词推上去（会重写清单+重启+收敛+过滤）。
- 若要让信息节点在**所有界面**都消失，需要在 `proxy-providers` 每个 provider 上加 provider 级
  `filter`/`exclude-filter`（节点不加载）。但 provider 段是 clashctl 按清单生成的，
  每次展开都会被重写 → 要跟组级过滤一样"每次同步后重新注入"。
  **尚未验证 mihomo v1.19.19 是否支持 provider 级 exclude-filter（要先小测再承诺）。**
