## 新增「拉黑节点」功能

需求：在节点选择页拉黑某个节点（或整个订阅/机场），自动换节点时不再选它。

### 数据模型（Models/LocalProfile.swift）
- 新增 `blockedNodes: [String]`（精确节点名）和 `blockedKeywords: [String]`（关键词，用于整批拉黑一个订阅/机场）。
- **手写 `init(from:)`**：旧 profile.json 没有这两个字段，合成解码会直接抛错 → 整个用户配置回落 default。
  全部字段改成 `decodeIfPresent ?? 默认值`。同时补了显式 memberwise init（定义了自定义 init 后不再自动合成）。
  已用本机真实的 `~/Library/Application Support/ClashRemote/profile.json` 验证能原样解开。
- **拉黑 ≠ 隐藏**：拆成 `isBlocked`（用户拉黑）/ `isFilteredOut`（关键词+地区+白名单，展示层）/ `shouldExcludeNode`（= 两者取并，自动切换用）。
  NodesBoard 的 flattenLeaves 改用 `isFilteredOut` → 被拉黑的节点灰掉留在列表里、可一键解除；
  拉黑只约束"自动换节点"，手动点选仍然可用。
- `nodeExcludeRegex()` 现在 = filterKeywords + blockedKeywords + blockedNodes，让路由器上的「节点选择」组也不含拉黑项。

### 自动切换（App/AppState.swift）
- `evaluateFailover` 开头算 `leafBlocked`：被拉黑的当前节点**强制换走**，跳过三个"保持现状"分支
  （阈值内保持 / 整组测速复核为通 / 45ms 抖动保护），也不再浪费时间测它（delay 直接置 -1）。
- 新增 `blockNode` / `blockKeyword` / `unblockNode` / `unblockKeyword` / `clearBlocklist` /
  `nodesMatching(keyword:)`（预览命中数）/ `suggestedBlockKeyword(for:)`（先拿本地订阅名去套节点名，
  套不上就按分隔符切词挑第一个非地区词 —— 本机订阅叫「乌拉VPN」「渔云CloudFisher」，正好能套上）。
- `finishBlocking` 在拉黑后如果当前叶子被命中，立刻 `evaluateFailover(manual: true)` 换走。
- `notifyNoFailoverCandidate` 现在会点出"是黑名单挡掉了 N 项"，避免用户以为节点全挂了。

### UI
- `NodesBoard`：NodeCard 右上角拉黑按钮（常显 0.25、hover 全亮，避免入口被忽略）+ 右键菜单；

- `ProfileTab`：新增「黑名单」卡片（按关键词 / 按节点名两组，各自解除、全部解除、同步过滤到路由器）。

### 设备守护（Network/NodeFailoverScript.swift）
- 脚本新增 `matches_line`（精确匹配，区分大小写）/ `is_blocked`，`is_excluded` 第一件事就判黑名单。

## 环境发现（重要）

**本机只有 CommandLineTools，没有完整 Xcode → CLT 里没有 `XCTest.framework`，`swift test` 直接报
`no such module 'XCTest'`，跟代码无关，是既有环境问题（`/Library/Developer/CommandLineTools/Library/Developer/Frameworks`
里只有 `Testing.framework` 即 swift-testing，没有 XCTest）。**

在没有 XCTest 的情况下验证 Swift 逻辑的可行套路（本次实测有效）：
1. `swiftc -O -o /tmp/x/verify <几个自包含源文件> /tmp/x/main.swift` —— 挑依赖最小的文件组
   （LocalProfile.swift / Models.swift / NodeFailoverScript.swift 只依赖 Foundation），
   把缺的小工具（如 `JSONValue`）从 HTTPClient.swift 抄一份最小副本放进 /tmp，然后 `main.swift` 里手写断言。
   实测用来验证：编解码兼容、真实 profile.json 升级不丢配置、filter 正则命中。
2. 让校验程序把生成的 shell 脚本/conf 导出到 /tmp，再用 `sh -n` 查语法、
   用 `awk '/^cmd=/{exit}{print}'` 抽出函数定义部分 `.` 进来真跑函数做行为断言。
   比"肉眼看脚本"可靠得多。
3. 构建仍要 `swift build --disable-sandbox`（会话内核 sandbox 里 sandbox-exec 被禁）。
   build.sh 里没有这个 flag，所以会话里要内联跑，或给 build.sh 补上。

# 追加：「固定当前节点」功能（同一天下午）

需求：固定节点 = 不再切换（除非超时）；**浏览器守护面板里也要能用**。

## 关键约束（决定了整个设计）

`Resources/cr-failover.html` 是**纯静态页**（由 mihomo 的 external-ui 提供、与 API 同源），
只能调 mihomo API（`/configs`、`/proxies`、`/connections`），**写不了路由器上的 conf 文件**；
跨源去够 LuCI（cgi-io）/ UFI（签名 root shell）既过不了 CORS 也等于把 root 权限交给一个网页。
→ **"面板上放一个写配置的固定开关"这条路走不通。**
也评估过在设备上让脚本用 `nc` 自起一个迷你 HTTP 控制端口，但 busybox/toybox 的 nc 行为差异大、
要手写 CORS preflight、而且当时路由器不可达（本机在 10.22.161.x）无法实测 → 放弃。

## 解法：「谁手动改了节点，就固定谁」——不需要任何新的写入通道

- 脚本新增 `PINFILE`（猫猫 `/data/clash/Scripts/node-failover.pin`，OpenClash `/etc/openclash/clashremote-failover.pin`），
  记「脚本自己选定的节点」。
- 每轮 `once()`：当前 leaf 与 PINFILE 不一致 = **别处改的**（面板点节点 / App 手动选 / 其它客户端）
  → 视为用户的明确意愿，**固定住不动**（再慢也不换）。脚本自己换完节点会更新 PINFILE → 不会被误判。
- 被固定的节点真超时 → 正常换走 → PINFILE 跟上 → 自动模式恢复。**这正好就是"固定，除非超时"**。
- `loop()` 启动时 `rm -f "$PINFILE"`：守护重启后内核选中的节点可能跟上次不一样，留着旧基线会被误判成
  "有人手动固定" → 基线只在进程生命周期内有效（App 侧的固定另有 `PIN_MODE` 走 conf，是持久的）。
- 被筛选/拉黑的当前节点**不享受固定**（PIN_NODE 清空，直接换走）。

## 面板（cr-failover.html）

- 脚本 `set_status` 的 JSON 新增 `pinMode` / `pin` / `auto` 三个字段。
- 面板读它显示「🔒 已固定 xxx（手动选过这个节点 / App 里打开的固定），只有超时才换」。
- **「恢复自动」按钮** = 面板把主组 PUT 回 `auto`（脚本上次自己选定的节点）→ 脚本下一轮就判定为自动模式。
  `pinMode=1`（App 里打开的固定）时不显示这个按钮 —— 点了也没用，别给假按钮。
- 节点列表上方加提示「点节点 = 固定它：除非超时，否则不会被自动换走」，点节点的 toast 改成「已切换并固定」。

## App 侧

- `LocalProfile.pinnedNode` + `effectiveFailoverThreshold`（固定时归零）。
- `evaluateFailover` 两处 `profile.failoverThreshold` → `profile.effectiveFailoverThreshold`
  （保持分支与"抖动复核"分支同时生效，语义自洽）。
- conf 输出 `PIN_MODE=1/0`，**阈值原值保留**（关掉固定要能恢复）。
- UI：节点页「固定当前节点」开关 + 当前节点旁的「已固定」标记；本地配置页同一开关，固定时阈值 Stepper 置灰。
- `DeviceFailoverStatus.phaseTitle` 认识 `pinned` 前缀 → "已固定当前节点，只有超时才换"。
- 卸载守护时清理 pin 文件（两个 Service 的 uninstall 都改了）。

## 本轮新验证手法（值得复用）

- **面板 JS 离线跑**：把 `<script>` 抽出来（python 正则），用 `node --check` 查语法；
  再用 `node` 的 `vm` mock 掉 `document` / `fetch` / `setInterval`，
  直接调 `loadDaemon` / `paintPin` / `restoreAuto` 做断言（7 项：三种固定文案、按钮显隐条件、
  读不到文件不崩、App 固定时不发 PUT、恢复自动会 PUT 到 auto 且组名 URL 编码正确）。
  坑：mock 的 response 要同时有 `text()` 和 `json()`；vm 里 `const` 不挂到 context，要显式 `globalThis.__x = x` 暴露。
- **守护脚本用假 mihomo API 跑真实 `once()`**：source 掉脚本函数（截到 `^cmd=`），
  覆盖 `http()` 返回预置 JSON（/version、/configs、/proxies/*、/group/*/delay），
  并把 TMPDIR/PINFILE/STATUSFILE/JSONFILE/HISTFILE 全部改写到 /tmp（脚本原本写 /data/clash）。
  8 个场景全绿：首次建基线 / 手动改→固定不换 / 固定中超时→换走并解除 / PIN_MODE=1 不换 /
  超阈值换 / 阈值内不换 / 阈值 0 慢也不换 / 被拉黑必须换。
  坑：`grep -c` 无匹配时既输出 0 又返回退出码 1，`|| echo 0` 会变成两行 "0"。

# 追加：把新版装到 /Applications（同日 20:25）

用户说「重新安装」= 覆盖安装到 `/Applications`（我当时问的就是这个）。

流程（全部在 `dangerouslyDisableSandbox` 下跑，因为要写 /Applications）：

```bash
OLD="/Applications/Clash Remote.app"
BAK="/Applications/.Clash Remote.pre-pin.app"
NEW="/Users/don/Documents/项目/ClashRemote/dist/Clash Remote.app"
rm -rf "$BAK" && mv "$OLD" "$BAK"     # 先 mv 再铺新版：中途失败旧版还在，比 rm -rf 稳
ditto "$NEW" "$OLD"
xattr -dr com.apple.quarantine "$OLD" 2>/dev/null || true
codesign --force --sign - --timestamp=none "$OLD"
open "$OLD"
```

- 备份命名沿用用户既有习惯 `/Applications/.Clash Remote.pre-*.app`（已有 previous / pre-ui / pre-fix / pre-final 四个）。
- 装完是 `1.1`，PID 起来后停在 `/Applications/...`（用 `pgrep -fl ClashRemote` + `ps -o etime,stat` 确认没秒退）。

## 本地网络权限 plist 的正确解析（修正之前的记忆）

`/Library/Preferences/com.apple.networkextension.plist` 的 `plutil -p` 输出里：

- `"Path"` / `"SigningIdentifier"` 是 **UID 引用**：`<CFKeyedArchiverUID 0x.. [0x..]>{value = 354}`，
  要靠同文件里的 `354 => "/Applications/..."` 这张表解引用。
- `"MulticastPreferenceSet"` / `"DenyMulticast"` 是**直接布尔值**（`=> true` / `=> false`），不是 UID！
  只按 UID 写解析器会把它们读成 None（我第一版就踩了），误判成"未授权"。
- 判定：`MulticastPreferenceSet == true && DenyMulticast == false` = 已授权。
- 实测本机有 **2 条** `dev.don.ClashRemote` 记录（一条指向 `dist/...`、一条指向 `/Applications/...`），
  两条都是已授权 —— 说明之前有会话直接从 dist 运行过。重装到同一路径会复用同名路径那条。
  记录里的 `DesignatedRequirement` 对 ad-hoc 签名是含 cdhash 的，所以**每次重签都可能让系统重新问一次**，
  这也是"同一 bundle id 出现多条记录"的成因。
- 完整解析脚本见本次会话（正则拆 `plutil -p` 的对象块 + 解 UID 表，顺手把两种值形态都处理掉）。
